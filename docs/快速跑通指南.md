## 4. 准备 Dify 知识库

当前主流程只需要导入这个工作流：

```text
dify/mdm_workflow.yml
```

后端负责上传校验、摄入匹配、粗筛、明显不相关记录写库、候选保存和人工审核任务创建。Dify 主工作流负责用 Loop 循环拉取高置信候选批次，并在循环内使用知识库检索和大模型选择主标题。

在 Dify 里先创建一个知识库，建议放这些内容：

- 品牌别名，例如 `MS = Microsoft`。
- 制造商归一化规则，例如 `Adobe Systems = Adobe`。
- 主标题选择规则，例如优先选择包含品牌、产品名、版本号、授权类型的标题。
- 正确匹配样例和错误匹配样例。

导入 `dify/mdm_workflow.yml` 后，打开 Loop 里面的“检索主数据知识库”节点，把这个占位数据集 ID：

```text
00000000-0000-0000-0000-000000000000
```

替换成你刚创建的 Dify 知识库 ID。

## 6. 在 Dify 里配置主工作流 API 地址

因为你的 Dify 是本地 Docker 部署，Dify 容器访问宿主机服务时要用：

```text
http://host.docker.internal:8000
```

导入主工作流：

```text
dify/mdm_workflow.yml
```

然后在 Dify 工作流环境变量里确认：

```text
MDM_API_BASE=http://host.docker.internal:8000
```

注意：`MDM_API_BASE` 优先在 Dify 工作流的“环境变量”里填写，不建议直接写进 `dify/docker/.env`。

原因是：

- `dify/docker/.env` 是 Dify 服务自身的 Docker 启动配置。
- `MDM_API_BASE` 是这个 MDM 工作流调用外部 API 时使用的变量。
- 导入 `dify/mdm_workflow.yml` 后，工作流里已经带了这个变量，通常只需要在 Dify 页面里确认或修改它。

如果你一定要写进 `dify/docker/.env`，可以加在文件末尾：

```text
MDM_API_BASE=http://host.docker.internal:8000
```

但仅写到 Docker `.env` 不一定会自动变成 Dify 工作流变量，最终仍以工作流页面里的 `MDM_API_BASE` 为准。

- `循环处理高置信候选`：Dify Loop 会按批次调用 `/candidate-batch`，每批经过知识库检索和大模型选择后调用 `/commit-llm-batch` 写入数据库。

## 10. 清空 SQLite 主数据库

如果你想重新从 `tableA + tableB` 初始化，但接口返回：

```json
{"valid": false, "database_has_data": true, "errors": ["database has data: upload one incoming CSV"]}
```

说明当前 SQLite 里已经有主数据。可以清空业务表后重新跑初始化。

进入项目目录：

```bash
cd /Users/sheeprose/Documents/mdm_data
```

执行：

```bash
python3 - <<'PY'
import sqlite3
from pathlib import Path

db_path = Path("artifacts/mdm.sqlite3")
if not db_path.exists():
    print("数据库文件不存在，无需清空")
    raise SystemExit

connection = sqlite3.connect(db_path)
for table in [
    "golden_records",
    "entities",
    "entity_aliases",
    "source_record_links",
    "match_decisions",
    "action_log",
    "review_tasks",
]:
    connection.execute(f"DELETE FROM {table}")
connection.commit()
connection.close()
print("SQLite 主数据库已清空")
PY
```

然后重新检查：

```text
http://127.0.0.1:8000/health
```

看到：

```json
"has_master_data": false
```

就可以重新按“第一次运行工作流怎么填”执行。

## 10.1 确认唯一实体表

工作流跑完后，先执行精确同名实体合并：

```bash
curl -sS -X POST http://127.0.0.1:8000/admin/merge-duplicate-alias-entities
```

再执行质量审计：

```bash
curl -sS http://127.0.0.1:8000/admin/entity-quality
```

结果里必须满足：

```json
{
  "valid": true,
  "entity_count": 2999,
  "golden_records_count": 2999,
  "duplicate_golden_entity_id_count": 0,
  "null_golden_entity_id_count": 0,
  "duplicate_source_link_count": 0,
  "duplicate_normalized_alias_count": 0
}
```

含义：

- `entities` 是真正的唯一实体主数据表。
- `golden_records` 是兼容展示表，必须和 `entities` 一实体一行。
- `source_record_links` 保证每条来源记录只指向一个实体。
- `duplicate_normalized_alias_count=0` 表示没有完全同名 alias 分散在多个实体上。

## 11. 最常见问题

### Dify 调不到服务

检查 Dify 里是不是：

```text
MDM_API_BASE=http://host.docker.internal:8000
```

不要在 Docker 版 Dify 里填：

```text
http://127.0.0.1:8000
```

因为那会指向 Dify 容器自己，不是你的电脑宿主机。

### 报错：被 SSRF 保护封锁

如果 Dify 报：

```text
Access to 'http://host.docker.internal:8000/ingest-and-match' was blocked by SSRF protection
```

说明 Dify 的 SSRF 代理默认禁止访问本机或内网地址。需要把 `host.docker.internal` 加入 SSRF 白名单。

打开 Dify 的 Docker `.env` 文件，在末尾加入：

```text
SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=host.docker.internal
```

然后在 Dify 的 `docker` 目录执行：

```bash
docker compose up -d
```

如果仍不生效，重启 SSRF 代理和 API：

```bash
docker compose restart ssrf_proxy api worker
```

再回到 Dify 工作流里重新运行“摄入并匹配”节点。

### CSV 字段不匹配

CSV 至少要有：

```text
id,title,manufacturer,price
```

也支持这些常见别名：

```text
product_id -> id
sku -> id
name -> title
product_name -> title
brand -> manufacturer
maker -> manufacturer
vendor -> manufacturer
list_price -> price
amount -> price
```

### 报错：json body type should have exactly one item

这是 Dify 1.15 的 HTTP 请求节点校验规则。JSON body 不能拆成多个 key/value item，必须写成一个完整 JSON 对象。

我已经修正了：

```text
dify/mdm_workflow.yml
```

如果你已经导入过旧版本工作流，处理方式二选一：

1. 删除旧工作流，重新导入新的 `dify/mdm_workflow.yml`。
2. 手动打开报错的 HTTP 节点，把 Body 改成一个 JSON 对象。

例如“摄入并匹配”节点的 Body 应该是一个整体：

```json
{
  "table_a_path": "{{#start.table_a_path#}}",
  "table_b_path": "{{#start.table_b_path#}}",
  "incoming_csv_path": "{{#start.incoming_csv_path#}}",
  "threshold": {{#start.threshold#}}
}
```

### 报错：Request failed with status code 422

新版本主工作流会在 Loop 内调用：

```text
/candidate-batch -> 知识库检索 -> 大模型知识库匹配 -> /commit-llm-batch
```

所以如果还遇到 422，优先检查你导入的是不是旧工作流。

主工作流里应该能看到这个 Loop 节点：

```text
循环处理高置信候选
```

Loop 内“写入当前批次大模型结果”的 Body 现在只发送“转义大模型输出”节点生成的完整 JSON：

```text
{{#prepare_llm_result.commit_body_json#}}
```

如果你的工作流里还能看到旧节点“处理全部高置信候选”或“检查并创建人工审核任务”，删除旧工作流并重新导入 `dify/mdm_workflow.yml`。

### 报错：Reached maximum retries for URL /commit-llm-batch

如果 Dify 在“写入当前批次大模型结果”节点报：

```text
Reached maximum retries for URL http://host.docker.internal:8000/commit-llm-batch
```

通常不是网络断了，而是大模型输出不是严格 JSON，导致提交接口收不到可解析的 `records`。

处理步骤：

1. 确认服务可访问：

```text
http://127.0.0.1:8000/health
```

2. 如果刚修改过 Python 代码，必须重启 MDM API：

```bash
cd /Users/sheeprose/Documents/mdm_data
export PUBLIC_REVIEW_BASE_URL='http://127.0.0.1:8000'
python3 -m uvicorn mdm_matching.service:app --host 0.0.0.0 --port 8000
```

3. 检查“大模型知识库匹配”节点是否只返回类似下面的 JSON，不要 Markdown：

```json
{"records":[{"chosen_title":"...","chosen_record":{},"confidence":0.95,"reason":"..."}]}
```

### 为什么大模型后还会进入人工审核检查

这是预期行为。

一次摄入结果里可能同时包含：

- `match_run_id`：完整粗筛结果的编号。
- `high_confidence_candidates`：高置信候选预览；完整高置信候选保存在后端。
- `human_review_candidates`：低置信候选预览；完整低置信候选保存在后端。

所以当前工作流是：

```text
摄入并匹配
-> 返回 match_run_id
-> 后端已经创建低置信人工审核任务
-> 如果有高置信候选：进入 Dify Loop
-> 每轮调用 /candidate-batch 拉取当前批次
-> Dify 知识库检索 + 大模型选择主标题
-> 调用 /commit-llm-batch 写入当前批次
-> 结束
```

`/candidate-batch` 和 `/commit-llm-batch` 是主工作流 Loop 内部使用的接口。

如果没有低置信候选，`创建人工审核任务` 会返回：

```json
{"status": "no_review_required", "review_url": null}
```

如果有低置信候选，会返回：

```json
{"status": "review_created", "review_url": "http://127.0.0.1:8000/review/..."}
```

### `completed` 是在哪里完成的

`completed` 是后端在“摄入并匹配”阶段就完成的。

触发条件是：粗筛后没有任何疑似匹配候选。

这种情况下，后端会直接把新记录写入数据库，并返回：

```json
{"status": "completed"}
```

Dify 看到 `completed` 后只进入结束节点，不再调用大模型或人工审核。

### 工作流停在“粗筛候选分流”

如果 Dify 看起来停在“粗筛候选分流”，先看“摄入并匹配”节点是否失败。

这类问题最常见的原因是 `/ingest-and-match` 返回内容太大。Dify 1.15.0 的 HTTP 节点对文本输出有限制，日志里会出现：

```text
Text size is too large, max size is 1.00 MB
```

当前版本已经改为：

```text
后端保存完整粗筛结果 -> 返回 match_run_id
Dify 只接收精简后的分流摘要
高置信候选通过 Dify Loop 调用 /candidate-batch 和 /commit-llm-batch 分批处理
低置信候选通过分页人工审核页面处理
```

如果仍然停在这里，确认 8000 服务已经重启，并且 Dify 调用的是最新后端代码。

### 人工审核链接打不开

确认服务仍在运行：

```text
http://127.0.0.1:8000/health
```

如果服务停了，重新执行启动命令。

### 报错：address already in use

如果启动 MDM API 时看到：

```text
ERROR: [Errno 48] error while attempting to bind on address ('0.0.0.0', 8000): address already in use
```

说明 8000 端口已经有进程在监听。先检查它是不是已经启动好的 MDM API：

```bash
curl -sS http://127.0.0.1:8000/health
```

如果返回类似：

```json
{"ok": true}
```

说明服务已经可用，不需要再启动第二个。

如果你刚改过代码，必须重启服务，先查占用端口的进程：

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

会看到类似：

```text
COMMAND     PID      USER   FD   TYPE   DEVICE SIZE/OFF NODE NAME
python3.1  37300    ...    10u  IPv4   ...    0t0      TCP *:8000 (LISTEN)
```

记下 `PID`，然后停止它：

```bash
kill 37300
```

再重新启动：

```bash
cd /Users/sheeprose/Documents/mdm_data
export PUBLIC_REVIEW_BASE_URL='http://127.0.0.1:8000'
python3 -m uvicorn mdm_matching.service:app --host 0.0.0.0 --port 8000
```

如果 `kill PID` 后还是占用，再查一次 `lsof`，确认是不是有新的 PID。不要直接反复启动多个 uvicorn。
