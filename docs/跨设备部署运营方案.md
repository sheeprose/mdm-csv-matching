# MDM+Dify 跨设备部署运营方案

本文档用于在另一台电脑上快速部署并运营当前 MDM CSV 主数据匹配流程。目标是：拿到项目代码、CSV 数据和 Dify 工作流后，可以稳定跑出一张“唯一实体主数据表”。

## 1. 总体部署形态

推荐架构：

```text
Dify 1.15.0 Docker 工作流
        |
        | HTTP: http://host.docker.internal:8000
        v
FastAPI MDM 服务
        |
        | SQLAlchemy
        v
SQLite 或 MySQL
```

职责划分：

- Dify：工作流编排、知识库检索、大模型结构化输出、循环调用后端。
- FastAPI：CSV 校验、预处理、粗筛、XGBoost/MLP/词法评分、实体聚类、写库、最终质量收尾。
- 数据库：保存唯一实体、黄金记录、源记录映射、别名和操作日志。

生产环境建议用 MySQL。个人演示和调试可以先用 SQLite。

## 2. 需要拷贝到新电脑的文件

必须拷贝：

```text
mdm_matching/
dify/mdm_workflow.yml
requirements.txt
structured_amazon_google/
docs/
```

可选拷贝：

```text
artifacts/mdm_matcher.joblib
artifacts/metrics.json
```

不建议直接拷贝到生产新库：

```text
artifacts/mdm.sqlite3
artifacts/match_runs/
artifacts/mdm_api.log
```

原因：这些是某次运行产生的数据库和运行记录。新设备建议重新初始化数据库并重新跑工作流。

## 3. 新设备基础环境

最低要求：

```text
Python: 3.10+
Docker Desktop: 已安装并可运行 Dify
Dify: 1.15.0
MySQL: 8.x，可选
```

进入项目目录：

```bash
cd /path/to/mdm_data
```

创建虚拟环境：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
```

如果新电脑没有模型文件，训练模型：

```bash
python3 -m mdm_matching.train --data-dir structured_amazon_google --output-dir artifacts
```

训练成功后应生成：

```text
artifacts/mdm_matcher.joblib
artifacts/metrics.json
```

## 4. 数据库模式

### 4.1 SQLite 调试模式

不设置 `MDM_DATABASE_URL` 时默认使用：

```text
sqlite:///artifacts/mdm.sqlite3
```

适合本地演示，启动命令：

```bash
export PUBLIC_REVIEW_BASE_URL='http://127.0.0.1:8000'
python3 -m uvicorn mdm_matching.service:app --host 0.0.0.0 --port 8000
```

### 4.2 MySQL 运营模式

创建数据库：

```sql
CREATE DATABASE mdm_data CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'mdm_user'@'%' IDENTIFIED BY 'mdm_password';
GRANT ALL PRIVILEGES ON mdm_data.* TO 'mdm_user'@'%';
FLUSH PRIVILEGES;
```

启动服务前设置：

```bash
export MDM_DATABASE_URL='mysql+pymysql://mdm_user:mdm_password@127.0.0.1:3306/mdm_data?charset=utf8mb4'
export PUBLIC_REVIEW_BASE_URL='http://127.0.0.1:8000'
python3 -m uvicorn mdm_matching.service:app --host 0.0.0.0 --port 8000
```

服务首次启动会自动建表和建索引。

核心唯一约束：

```text
source_record_links(source_table, source_id) 唯一
golden_records(entity_id) 唯一
```

## 6. Dify Docker 配置

Dify 是 Docker 本地部署时，容器访问宿主机 FastAPI 使用：

```text
http://host.docker.internal:8000
```

导入工作流：

```text
dify/mdm_workflow.yml
```

在 Dify 工作流环境变量里确认：

```text
MDM_API_BASE=http://host.docker.internal:8000
```

如果遇到 SSRF 拦截，需要在 Dify Docker 配置中允许宿主机域名。进入 Dify Docker 目录后，在 `.env` 中确认或添加：

```text
SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=host.docker.internal
```

然后重启 Dify：

```bash
docker compose down
docker compose up -d
```

检查 Dify：

```bash
docker compose ps
```

Dify 主界面通常是：

```text
http://localhost
```

## 7. Dify 知识库

工作流里有“检索主数据知识库”节点。新设备导入后，需要把占位知识库 ID：

```text
00000000-0000-0000-0000-000000000000
```

替换为你在新 Dify 里创建的知识库 ID。

知识库建议放：

- 品牌别名：`MS = Microsoft`，`HP = Hewlett Packard`。
- 制造商归一化：`Adobe Systems = Adobe`，`Apple Computer = Apple`。
- 实体拆分规则：不同版本、平台、授权数量、套装内容不能合并。
- 正确匹配样例。
- 错误匹配样例。

## 8. 第一次初始化运行

数据库为空时，在 Dify 开始节点填写：

```text
tableA CSV 本地路径或 URL:
/path/to/mdm_data/structured_amazon_google/tableA.csv

tableB CSV 本地路径或 URL:
/path/to/mdm_data/structured_amazon_google/tableB.csv

待匹配 CSV 本地路径或 URL:
留空

匹配置信度阈值:
0.9
```

字段要求：

```text
id,title,manufacturer,price
```

工作流会执行：

```text
摄入并匹配
-> Dify Loop 分批拉取冲突簇
-> 知识库检索
-> 大模型结构化实体分组
-> 写入当前冲突簇结果
-> 最终质量收尾
-> 结束
```

## 9. 后续增量运行

数据库已有主数据时，只填新增 CSV：

```text
tableA CSV 本地路径或 URL:
留空

tableB CSV 本地路径或 URL:
留空

待匹配 CSV 本地路径或 URL:
/path/to/incoming.csv

匹配置信度阈值:
0.9
```

新增 CSV 字段仍需能映射到：

```text
id,title,manufacturer,price
```

## 10. 关键参数

后端参数：

```text
MDM_AUTO_MERGE_CONFIDENCE=0.94
MDM_LLM_CLUSTER_MIN_CONFIDENCE=0.78
MDM_AMBIGUOUS_MARGIN=0.04
```

Dify 工作流参数：

```text
大模型温度 temperature: 0
大模型最大输出 max_tokens: 8192
大模型重试 max_retries: 2
Loop 每批 limit: 30
Loop 最大次数 loop_count: 100
开始节点 threshold: 0.9
```

推荐默认值：

```text
threshold=0.9
limit=30
```

如果模型调用成本过高，可以把 `MDM_LLM_CLUSTER_MIN_CONFIDENCE` 提高到 `0.82` 或 `0.85`，但召回会下降。

## 11. 最终质量验收

调用质量接口：

```bash
curl -sS 'http://127.0.0.1:8000/admin/entity-quality?expected_table1=1363&expected_table2=3226'
```

合格条件：

```text
valid=true
golden_records_count == entity_count
duplicate_golden_entity_id_count == 0
null_golden_entity_id_count == 0
duplicate_source_link_count == 0
table1_source_link_count == expected_table1
table2_source_link_count == expected_table2
uncertain_decision_count == 0
```

当前样例数据的合格结果应类似：

```text
entity_count: 4200
golden_records_count: 4200
table1_source_link_count: 1363
table2_source_link_count: 3226
duplicate_source_link_count: 0
uncertain_decision_count: 0
valid: true
```

`duplicate_canonical_title_count` 和 `duplicate_normalized_alias_count` 是风险提示，不是硬失败。对 `software`、`quickbooks (r)`、`deposit slips` 这类泛称，系统会保守保留，不自动合并。

## 12. 常见故障

### 12.1 8000 端口占用

查看占用：

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

停止旧进程：

```bash
kill <PID>
```

重新启动服务。

### 12.2 Dify 访问 API 被 SSRF 拦截

确认 Dify Docker `.env`：

```text
SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=host.docker.internal
```

重启 Dify：

```bash
docker compose down
docker compose up -d
```

### 12.3 Dify 显示 422 或 400

先看后端日志和质量接口：

```bash
curl -sS http://127.0.0.1:8000/health
curl -sS http://127.0.0.1:8000/admin/entity-quality
```

当前版本中，大模型输出异常不会直接写坏数据。工作流最后的“最终质量收尾”会补齐未处理簇。

### 12.4 想清空 SQLite 重跑

确认只在调试库执行。进入项目目录后：

```bash
python3 - <<'PY'
import sqlite3
from pathlib import Path

db = Path("artifacts/mdm.sqlite3")
con = sqlite3.connect(db)
for table in [
    "golden_records",
    "entities",
    "entity_aliases",
    "source_record_links",
    "match_decisions",
    "review_tasks",
    "action_log",
]:
    con.execute(f"DELETE FROM {table}")
con.commit()
con.close()
print("SQLite 业务表已清空")
PY
```

MySQL 清空需谨慎，建议只在测试库执行：

```sql
SET FOREIGN_KEY_CHECKS=0;
TRUNCATE TABLE golden_records;
TRUNCATE TABLE entities;
TRUNCATE TABLE entity_aliases;
TRUNCATE TABLE source_record_links;
TRUNCATE TABLE match_decisions;
TRUNCATE TABLE review_tasks;
TRUNCATE TABLE action_log;
SET FOREIGN_KEY_CHECKS=1;
```
